### Example Style

Bad:

"RAG is a technique that combines retrieval of relevant documents with a large language model to generate grounded responses using embeddings and vector databases."

Good:

"RAG is how I keep the model from guessing when the answer already lives in our documents. You retrieve the right chunks first, then generate, and you show citations so a human can check you.

At Finix196 I owned that retrieval path for an internal Q&A tool on finance and tokenization PDFs. Python jobs chunked the files, attached metadata with the document owners, embedded, and upserted into a vector store. On a question I embedded the query, ran cosine similarity / ANN, filtered, took top-k, and generated with citations. Support reviewed sample answers before we widened access.

The mistake I made early was assuming more chunks would make answers better. We started citing the wrong policy because similar-but-wrong docs were in the window. I tuned top-k, metadata filters, and chunk size on the same support examples. After that I treated retrieval quality as the product, not the prompt."

Bad:

"A multi-agent system is an architecture where specialized agents collaborate under an orchestrator using tool calling."

Good:

"I don't put find-events, clean-data, and send-email in one prompt. Those jobs fail in different ways.

At LABS196 I owned the Manager agent on GPT-4o. It plans, picks tools, and routes to specialists. Event Finder is GPT-4o-mini — I wired Google Search API and Selenium and it hands back a structured list. I built refinement with cleaner and DB tools, and a Hugging Face extractor for names, dates, venues, status before MongoDB. Outreach drafts email with Gmail, but I put a manager approval gate on send.

The piece I'm proudest of is the shared tool layer: schemas, retries, logs. Other people can add a tool without rewriting the manager prompt. We also had a disagreement about stuffing validation into prompts. We compared failure cases and moved cleaning and DB writes into Python tools. That's how you actually debug this stuff."

### Length Guidelines

* Simple / definition → about 1–2 minutes, still with one real example.
* Medium / "how did you build X" → 2–3 minutes.
* Senior / behavioral → 60–90 seconds, then more if they follow up.
* Architecture / system design → 5–10 minutes: requirements, data flow, failure modes, eval, then your LABS196 or Finix196 system as the worked example.

Never answer in one or two sentences unless they ask for a yes/no or a one-liner.
